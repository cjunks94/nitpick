# nitpick — security & operational review (against parent + repo CLAUDE.md)

Scope: `internal/server/`, `internal/ghapp/`, `internal/ghc/httpclient.go` (+ `pr.go`, `comments.go`, `statuscomment.go` where they touch the same boundary), `internal/provider/anthropic.go`, `internal/secrets/`, `internal/config/`, `cmd/serve.go`, `main.go`, `Dockerfile`, `.github/workflows/security.yml`, `.github/dependabot.yml`, `.env.example`, `DEPLOY.md`. Read-only; no files modified. All paths below are relative to `C:\Users\cj\Documents\side-projects\nitpick\`.

No high-severity finding. The load-bearing controls the repo CLAUDE.md names (HMAC-before-parse, fail-closed write gate, fork-config isolation, secret redaction, drain WaitGroup, opt-out flag shape) all check out in code. The findings are mostly standards gaps (request-ID middleware, retry/backoff, lint/coverage gates) and a handful of robustness holes around the GitHub boundary.

### 1. No retry/backoff on GitHub calls, and the head-SHA dedup is claimed before any of them succeed  [medium] serve / ghc
- where: `internal/server/webhook.go:810`, `internal/server/webhook.go:877-892`, `internal/ghc/httpclient.go:296-304`, `internal/ghapp/install.go:69-82`
- what: `shouldSkip` writes `h.seen[key] = time.Now()` (810) synchronously, then the review goroutine does `token, err := h.TokenSource.Token(ctx, t.InstallID)` / `raw, err := client.FetchDiff(ctx, repo, prNum)` and on any error just `log.Error(...)` + `return` (879-892). Every `ghc.HTTPClient` and `ghapp` call is a single `c.HTTPClient.Do(req)` with no retry, no 5xx handling, no `Retry-After`. A transient GitHub 502 or a token-mint hiccup therefore loses the review *and* marks that head SHA "already reviewed" for an hour; only a new push or a `/nitpick` comment recovers it. The same is true when `goReview` sheds on a full queue (line 313-317) or `overSpendCap` sheds (868-875): the `seen` claim was already made.
- standard: parent CLAUDE.md "Retry logic has exponential backoff" (review checklist), "Handle rate limiting with exponential backoff"; repo CLAUDE.md lists "No retry logic on the LLM provider" as known-absent but does not cover GitHub calls.
- fix: add a small `doWithRetry` in `httpclient.go` (3 attempts, 500ms→2s→8s, retry on connection error / 5xx / 429 / 403-with-`Retry-After`, never on 4xx otherwise) and use it from `Token`, `FetchDiff`, `FetchFile`, `FetchPR`, `PostReview`, `PostIssueComment`. Separately, move the `h.seen[key]` write out of `shouldSkip` into `reviewPR` just before the LLM call (or delete the key on the early-return error paths) so a failed or shed review is retried by GitHub's own redelivery instead of being deduped away.

### 2. Request-ID middleware deliberately skipped; access log line has no correlation ID  [medium] serve / logging
- where: `internal/server/server.go:139-158`, `internal/server/webhook.go:464-465`
- what: The comment is explicit: "Lightweight — skipping the full request-ID-middleware pattern (X-Request-ID echo, regex validation) since GitHub already sends X-GitHub-Delivery". The `withRequestLogging` line emits only `method/path/status/duration_ms`, so the per-request "http" log entry cannot be joined to the handler's `delivery_id`-scoped lines. The response carries no `X-Request-ID` either, and `deliveryID := r.Header.Get("X-GitHub-Delivery")` is attached to `log.With(...)` unvalidated — any header value, of any length or charset, is written into the JSON log as-is (slog JSON-escapes it, so it's not an injection, but the length is unbounded).
- standard: parent CLAUDE.md "Logging → Inject a request ID middleware that: honors a valid inbound X-Request-ID, validates against `^[a-zA-Z0-9_-]{1,128}$`, falls back to random with a sentinel, echoes it in the response". Partially met (delivery ID as correlation), not met on validation/echo/access-log.
- fix: In `withRequestLogging`, resolve `id := firstValid(X-Request-ID, X-GitHub-Delivery)` against the regex, fall back to `rand` hex (sentinel `"norand-"+time` on RNG error), set `w.Header().Set("X-Request-ID", id)`, put it on `r.Context()` and in the "http" log line; have `ServeHTTP` read it from context instead of the raw header. Roughly 25 lines, unit-testable without a port.

### 3. Two cost-control knobs have the exact "zero value disables the safety control" shape the repo warns about  [medium] serve / cost controls
- where: `internal/server/webhook.go:216-222`, `internal/server/webhook.go:262-282` (`ensureInit`), `internal/server/webhook.go:407-409`, `internal/server/webhook.go:417-419`
- what: `TriggerCooldown time.Duration` and `MaxSpendPerHourUSD float64` are exported, and `overSpendCap` returns `false` when `h.MaxSpendPerHourUSD <= 0`, `triggerCooledDown` returns `true` when `h.TriggerCooldown <= 0`. `ensureInit` repairs `seen`, `lastTrigger`, `sem`, `baseCtx`, `Logger` but not these two. So a `Handler{...}` struct literal (which the file says is "documented as supported and the test helper uses it") runs with no spend ceiling and no trigger cooldown. `NewHandler` sets both correctly, and `Run` uses `NewHandler`, so production is safe today — but the field comments ("Zero disables the cap") codify the shape the repo CLAUDE.md says "shipped once; don't reintroduce".
- standard: repo CLAUDE.md "Security flags are phrased as opt-OUTs so the zero value is safe … a `bool` can't tell 'unset' from 'explicitly false'"; parent "Cost controls … are load-bearing".
- fix: Make disabling explicit rather than the zero value: either `DisableSpendCap bool` / `DisableTriggerCooldown bool` (opt-out) with `ensureInit` filling the defaults when the numeric field is zero, or use pointer types. Add a test that a bare `&Handler{}` still enforces both caps.

### 4. LLM output is posted to GitHub as API fields with no validation against the diff  [medium] ghc / input validation
- where: `internal/ghc/comments.go:32-45`, `internal/provider/anthropic.go:26-50` (`flexInt`), `internal/provider/anthropic.go:276-288`, `internal/server/webhook.go:1009-1018`
- what: `BuildReviewBody` maps each finding straight to `"path": c.File, "line": c.Line, "side": "RIGHT"`. `flexInt` accepts any int including 0 and negatives, and `unmarshalFindings` only normalises `Severity`; `File` is whatever string the model emitted. Nothing checks that `(File, Line)` is an added/context line present in `hunks`. GitHub rejects a review whose *any* comment is off-diff with 422, at which point `reviewPR` logs "post review" and returns — every valid finding in that batch is lost and the operator has already paid for it (the 422 row in DEPLOY.md's troubleshooting table blames "head moved", but a single hallucinated line number produces the same symptom). The prompt tells the model to use diff lines only, but a prompt instruction is not a boundary check.
- standard: parent CLAUDE.md "Input validation on all external data" / "Zod (or equivalent) for runtime validation at boundaries" — the model response is an external boundary.
- fix: Before `PostReview` in `reviewPR` (and in `cmd/review.go`), build a `map[file]set[line]` of `LineAdded`+context `NewLineNum`s from `hunks`, drop findings whose `(File, Line)` isn't in it, and log `"findings_dropped_unanchored"`. Also reject `Line <= 0` in `unmarshalFindings`. This is in `internal/server`/`ghc`, so no eval run is needed; keep `flexInt` itself untouched per the repo rule.

### 5. Outbound response bodies are read without a size cap  [medium] ghc / ghapp / HTTP hygiene
- where: `internal/ghc/httpclient.go:301`, `:393`, `:442`, `:508`, `:588`, `:622`; `internal/ghc/statuscomment.go:591`; `internal/ghapp/install.go:74`
- what: Every call does `body, _ := io.ReadAll(resp.Body)` (or `body, readErr := io.ReadAll(resp.Body)` in `listComments`). Inbound is capped (`io.LimitReader(r.Body, 5<<20)` at `webhook.go:468`) but outbound is not: `FetchDiff` on a PR that passes `MaxLinesPerPR` (based on the payload's `additions+deletions`) can still be tens of MB if lines are long; `FetchFile` checks `len(content) > maxContextFileBytes` *after* reading the whole body; the token-exchange body is read in full before `redactTokens(body, 300)`. Also, most calls discard the read error (`body, _ :=`), so a truncated diff parses as a shorter diff rather than failing.
- standard: hardening (parent's "Input validation on all external data" applied to responses; the repo already applies it inbound).
- fix: Wrap each `resp.Body` in `io.LimitReader(resp.Body, N+1)` with N = 8 MiB for diffs, `maxContextFileBytes+1` for `FetchFile`, 1 MiB for JSON endpoints, and treat `len(body) > N` as an error; check the `io.ReadAll` error everywhere instead of `_`. Setting a `User-Agent: nitpick/<version>` header at the same time is cheap and GitHub asks for it.

### 6. Dockerfile: no `.dockerignore`, `COPY . .`, `go mod download || true`, floating base tags, `gh` in the server image  [medium] infra
- where: `Dockerfile:2-11` (`FROM golang:1.24-alpine AS build` … `RUN go mod download || true` … `COPY . .` … `FROM alpine:3.20` … `apk add --no-cache github-cli ca-certificates`); repo root has no `.dockerignore`
- what: Non-root user (`USER nitpick`), multi-stage, `-ldflags="-s -w"`, `CGO_ENABLED=0` and no baked secrets are all correct. But with no `.dockerignore`, `COPY . .` copies the whole working tree — including a local `.env` (gitignored, but present on a dev box that ran the smoke-test in DEPLOY.md) and `.git/` — into the build stage's layer cache. `go mod download || true` masks a failed module fetch and lets `go build` re-fetch without `go.sum` verification context. `golang:1.24-alpine` / `alpine:3.20` are mutable tags rather than digests (Dependabot's `github-actions` ecosystem won't bump them; there is no `docker` ecosystem entry). `github-cli` is installed into the *serve* runtime image although `serve` never shells out — it exists only for `action.yml`'s `review` path, and widens the runtime attack surface.
- standard: parent "No secrets or credentials in code" (build context), Dependabot "weekly grouped updates"; the rest is hardening.
- fix: Add `.dockerignore` with `.env*`, `.git`, `eval/`, `*.md`, `nitpick*`; drop `|| true`; pin both `FROM` lines by digest and add a `package-ecosystem: docker` entry to `dependabot.yml`; either build two targets (`serve` without `gh`) or accept and document the extra binary.

### 7. A failed review is invisible on the PR  [medium] serve / ops
- where: `internal/server/webhook.go:877-892`, `:990-996`, `:1009-1018`
- what: Every failure path — token mint, `FetchDiff`, `ParseUnifiedDiff`, `provider review`, `PostReview` — is `log.Error(...); return`. The status comment (`BuildStatusCommentBody`) is only posted on success or on the "all files filtered" skip (line 925). So from the PR author's perspective a crashed review and a silent-clean review look identical (no comment at all vs. "no actionable findings"), and only someone reading Railway logs can tell. On the positive side: the HTTP responses are fixed strings (`"bad body"`, `"bad signature"`, `"bad json"`, `POST only`) and the status comment carries only count/cost/duration/model — no internal error text reaches GitHub or the HTTP client, which satisfies the "don't leak internals" rule.
- standard: parent "Error messages don't leak internal details" (met); parent "Structured logging with context" (met); the gap is operational visibility — hardening.
- fix: On provider/post failures, post a fixed-text status comment ("**nitpick** — review failed (see server logs, delivery `<id>`)") using the still-valid `ctx`; keep the wording static so no `err.Error()` ever reaches the PR.

### 8. Hourly spend cap is checked before a wait that can last 10+ minutes, and the comment says otherwise  [low] serve / cost controls
- where: `internal/server/webhook.go:403-405`, `:868-875`, `:960-965`, `:984-990`
- what: `overSpendCap` is documented as "Checked immediately before the LLM call so the guard reflects spend that landed while this review was queued", and `reviewPR` calls it at line 868 — but the CodeRabbit wait (`waitForCodeRabbit(waitCtx, …)` at 963, ceiling `maxCodeRabbitWaitTimeout = 10m` + `reviewPhaseBudget`) sits between that check and `reviewer.Review(...)` at 984. With `wait: true`, up to `defaultMaxConcurrentReviews` (4) reviews can each pass the cap, sleep 10 minutes while other reviews spend, then call the model. Overshoot is bounded (4 × one review's cost), so this is a comment/ordering bug, not an open bill. Otherwise every path to the provider is covered: `pull_request` → `shouldSkip` (MaxLines, bot, draft) → `goReview` (queue 32, sem 4) → `reviewPR` (cap); `/nitpick` → `triggerCooledDown` → `goReview` → write-access gate → MaxLines → `reviewPR` (cap). Escalation to Sonnet via `review.escalate` is only reachable with a trusted config (`configRef`) and still passes the same cap.
- standard: repo CLAUDE.md "Cost controls in `internal/server/webhook.go` … Don't relax one without checking what still bounds the bill".
- fix: Re-run `h.overSpendCap()` after the wait block (immediately before `reviewer.Review`) and update the comment at 403-405. Note the wait also pins a concurrency slot for its whole duration — consider taking the semaphore *after* the wait so a repo with `wait: true` can't hold 4 slots idle.

### 9. Model output and `.nitpick.yaml` parse errors land in the log stream  [low] logging
- where: `internal/provider/anthropic.go:145` → `internal/server/webhook.go:994`; `internal/server/webhook.go:1110-1113`; `internal/ghc/httpclient.go:303, 400, 447, 514, 590, 624`
- what: On a parse failure the provider returns `fmt.Errorf("parse findings: %w (raw: %s)", err, truncate(text, 200))` and `reviewPR` logs it verbatim (`log.Error("provider review", "err", err)`) — 200 bytes of the model's response, which quotes diff content by design. `fetchRepoConfig` logs the yaml.v3 error, which can embed a snippet of the offending `.nitpick.yaml` value (`cannot unmarshal !!str \`...\``). Every GitHub error path logs `truncate(string(body), 300|500)` of the response body. All three are on error paths only, the diff/context/notes are already run through `secrets.RedactBytes`/`SanitizeHunks` before the model sees them, and `ghapp.redactTokens` masks `gh[pousr]_` tokens in the token-exchange body — so this is bounded, not a live leak. Checked and clean: no log line includes the webhook payload, the diff, `.nitpick.yaml` contents, the installation token, the App private key, or the Anthropic key (`ParsePrivateKeyPEM` wraps jwt's error without the input; `Authorization` headers are never logged; `serve.go:31-32` only checks presence).
- standard: parent "Never log secret values, full PII, or full card numbers"; "PII/PCI data properly encrypted/masked in logs" — partial.
- fix: In `anthropic.go:145` pass the raw fragment through `secrets.RedactLine` (or drop it and log `len(text)` + first 40 bytes), and in `ghc` route the truncated error bodies through `ghapp.redactTokens`-style masking (move `redactTokens` to a shared helper). `anthropic.go` is on the "don't touch without eval" list, but this line is error-formatting only — still, isolate it as its own commit.

### 10. No 403/429 rate-limit handling; a rate-limited permission check reads as "not a collaborator"  [low] ghc / HTTP hygiene
- where: `internal/ghc/httpclient.go:394-397`, `:398-401`; no `Retry-After` / `X-RateLimit-Remaining` reference anywhere in `internal/`
- what: `RepoPermission` does `if resp.StatusCode == http.StatusNotFound || resp.StatusCode == http.StatusForbidden { return PermNone, nil }`. Failing closed is right, but GitHub also returns 403 for primary/secondary rate limits, so under a burst the `/nitpick` gate logs `"skip", "reason", "commenter lacks write access"` for a maintainer who has it. Other endpoints surface 403/429 as a generic `HTTP %d` error with no backoff. Timeouts are fine: `http.Client{Timeout: 30s}` in both `ghc.NewHTTPClient` (234-236) and `ghapp.NewInstallationTokenSource` (40), and every request uses `NewRequestWithContext` under a phase deadline. `Accept`, `X-GitHub-Api-Version`, and `Content-Type` on POSTs are all set. The Anthropic SDK default is 10 min per request with 2 retries (`anthropic-sdk-go@v1.70.1/client.go:312`, `requestconfig.go:173`), bounded in practice by `reviewCtx`'s 90 s; the comment at `webhook.go:822` ("the Anthropic SDK's internal timeout is 30s too") is wrong.
- standard: parent "Handle rate limiting with exponential backoff" — missing.
- fix: In `RepoPermission`, treat 403 as fail-closed *only* when `X-RateLimit-Remaining != "0"` and there is no `Retry-After`; otherwise return an error so the caller logs "rate limited" and releases the cooldown. Fold `Retry-After` honouring into the retry helper from finding 1. Fix the 30 s comment.

### 11. `ServeHTTP` does not refuse an empty webhook secret  [low] serve / webhook security
- where: `internal/server/signature.go:208-221`, `internal/server/webhook.go:474`, `internal/server/server.go:35-37`
- what: `VerifySignature` is correct — `hmac.Equal(want, got)` is constant-time, the prefix is checked, hex is decoded, and it runs before any `json.Unmarshal` (line 474 precedes 504). `Run` refuses to start without `GITHUB_WEBHOOK_SECRET`. But a `Handler` built directly (the struct-literal path the file supports) with `WebhookSecret: ""` still "verifies": an attacker who knows the secret is empty can sign anything with `hmac(sha256, "")`. Delivery-ID dedup and a replay window are absent: a captured signed `issue_comment` payload can be replayed once per `TriggerCooldown` (60 s) forever, and the write-access check passes because the original commenter had write. Capturing a payload requires breaking TLS to Railway, so exposure is low, but the `X-GitHub-Delivery` header (already read at 464) makes dedup a 10-line map.
- standard: hardening (repo CLAUDE.md "the zero value is safe" principle).
- fix: In `ServeHTTP`, `if h.WebhookSecret == "" { http.Error(w, "server misconfigured", 500); return }` (and a test). Add `seenDeliveries map[string]time.Time` with a 10-minute TTL keyed by `X-GitHub-Delivery`, reject repeats with 202 + `"skipped":"duplicate_delivery"`.

### 12. CI: no lint job, no coverage threshold; actions on floating tags except gitleaks; SHA comment is inconsistent  [low] ci
- where: `.github/workflows/security.yml:42-51`, `:126-131`; `.github/dependabot.yml:26-38`
- what: The workflow is otherwise good: a real `go test -race -coverprofile` job, `go mod verify`, `go vet`, weekly Monday cron, `go-version: stable` for govulncheck/gosec (the parent gotcha), `go-version-file: go.mod` for build, top-level `permissions: contents: read`, gitleaks job with `pull-requests: read` and the Dependabot skip, `persist-credentials: false` everywhere. Gaps: there is no lint step (`golangci-lint`/`staticcheck`), and coverage is uploaded with `fail_ci_if_error: false` and no threshold, so the "Test (coverage >= 80%)" and "Lint" required checks can't exist. `actions/checkout@v7`, `actions/setup-go@v7`, `codecov/codecov-action@v7` use mutable major tags while gitleaks is SHA-pinned with a rationale that applies equally to them; the pin's comment says "This SHA equals the v2.3.9 release" on line 128 and `# v3.0.0` on line 131. `dependabot.yml` groups `gomod` but the `github-actions` block has no `groups:`.
- standard: parent "Branch Protection → Status checks must pass: Build, Test (coverage >= 80%), Lint, Security scan"; "Dependabot — weekly grouped updates (… + github-actions)".
- fix: Add a `lint` job (`golangci-lint-action` SHA-pinned, or `go run honnef.co/go/tools/cmd/staticcheck`), gate coverage with a `go tool cover -func` awk step (`>= 80`), SHA-pin the three `actions/*`/codecov uses (Dependabot will keep the SHAs current), fix the v2.3.9/v3.0.0 comment, and add `groups: {actions: {patterns: ["*"]}}` to the github-actions block.

### 13. `.nitpick.yaml` is decoded non-strictly; unknown keys and typos silently no-op  [low] config / input validation
- where: `internal/config/config.go:364-376`
- what: `yaml.Unmarshal(b, &cfg)` ignores unknown fields, so `ignore_path:` (typo) or `review: { escalate: { modle: … } }` loads cleanly with the filter/escalation off. Validation that *is* present is good: `ValidatePatterns` compiles every glob at load, `EscalateConfig.validate` rejects half-set routing, `Duration` parsing bounds-checks overflow and negatives, escalate `model` is validated against `priceTable` in `NewAnthropic` (so a config can't name an unpriced model), size caps of 32 KiB config / 16 KiB notes are enforced in `fetchRepoConfig`, and `context_notes` goes through `secrets.RedactBytes`. `FetchFile` percent-escapes each path segment and rejects `..`. Webhook JSON uses lenient `json.Unmarshal`, which is correct for GitHub payloads that add fields.
- standard: parent "Input validation on all external data" — partial.
- fix: Decode with `dec := yaml.NewDecoder(bytes.NewReader(b)); dec.KnownFields(true)` and log the resulting error at WARN (still fall back to defaults) so an operator sees the typo in Railway logs; keep `Parse` lenient for the CLI if forward-compat matters, but at least surface it.

## Overall assessment

The security-critical core — HMAC verified before parsing, write-access gate that fails closed, fork-PR config read from the base ref, line-preserving secret redaction on everything that leaves the process, and a real drain WaitGroup behind SIGTERM — is implemented as the repo CLAUDE.md claims and is defensible line by line. What is missing is mostly the operational layer the parent standard asks for: a request-ID middleware, retry/backoff and rate-limit handling on GitHub calls, outbound body caps, and Lint/coverage gates in CI, plus one genuine robustness gap where unvalidated LLM line numbers can 422 an entire paid review. None of the findings is exploitable for money or data today given `NewHandler` defaults and TLS on Railway, so the right sequencing is findings 1, 4 and 3 first (they lose reviews or reintroduce a known bug shape), then 2/5/6 as a hygiene batch, then the low-severity doc and CI cleanups.
